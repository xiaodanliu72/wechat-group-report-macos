# 总结数据契约

消息原文来自 `messages.json` 的 `messages`，每条含稳定 `id`、时间、发送人、`type`、`text` 和 `details`（卡片、引用等）。统计来自 `metadata`。按导出顺序阅读全部消息，保留来源 ID；不要从时间、行号或卡片引用自行构造 ID。

`report.json` 必须采用如下形状。以下 ID 仅示意，实际必须换成当前导出中存在的 ID；每个栏目可含多项：

```json
{
  "reviewed_message_ids": ["全部已阅读消息的ID，按导出顺序"],
  "overview": {"text": "一段简短概览", "sources": ["实际消息ID"]},
  "topics": [{"text": "主要话题、明确的讨论结论或分歧", "sources": ["实际消息ID"]}],
  "todos": [{
    "text": "待办事项",
    "owner": "原文明示负责人，否则未明确",
    "deadline": "原文明示时间要求，否则未明确",
    "status": "有依据的当前状态，否则未明确",
    "sources": ["实际消息ID"]
  }],
  "confirmed": [{"text": "有明确依据的已确认或已解决事项", "sources": ["实际消息ID"]}],
  "unresolved": [{"text": "尚未解决的问题", "sources": ["实际消息ID"]}],
  "other": [{"text": "必要的其他信息", "sources": ["实际消息ID"]}]
}
```

- `reviewed_message_ids` 必须与消息列表的 ID 顺序完全一致，不遗漏、不重复；读完之后可用代码从原数据提取此数组，不能因此跳过阅读。
- `overview` 始终提供非空 `text`。其他栏目没有明确依据时用空数组 `[]`，渲染器会说明未提取到事项；不要为凑栏目编造结论。
- 有消息时，每一项包括概览都必须带非空 `sources`。一项有数个独立结论时分别列项或确保引用覆盖每个结论。避免引用全部消息掩盖证据不足。
- 无消息时使用 `reviewed_message_ids: []`，概览如“本机本次已同步窗口内未读取到消息，无法据此判断完整群历史”，概览 `sources: []`，其他栏目全为空数组。
- `owner` / `deadline` 没有明确依据时填“未明确”。群成员说“收到”不代表同意或认领；“同意”不代表执行完成；“建议”不代表决定。延期、取消、完成等后续消息优先更新状态，并引用前后证据。
- 相对日期按发言时间和时区解释，保留原文相对表述；有歧义时不强行换成绝对日期。
- 对业绩、政策、完成情况等群内陈述写“群内通报/某某表示”，不能当成外部核实事实。图片、视频、语音、表情只有类型信息时，不描述内容；语音有 `transcript_source` 才引用已有转写并注明来源。
- 对可解析卡片可写实际标题、链接或文件字段；引用消息正文可以辅助理解，但窗口外被引用内容不是本次独立导出消息，来源指向包含该引用的真实消息 ID。
- 不在报告放密钥、账号令牌或调试输出。不要增加无关个人资料；来源摘录限于核对结论所需信息。

从 `report.template.json` 开始填写；不要改动 `messages.json` / `messages.txt` 来让引用或统计通过。运行 `render` 会核验原始统计、时间边界、消息 ID、阅读覆盖和引用存在性，生成六个文件与 `validation.json`。`semantic_review` 只是语义核对责任说明，程序不能证明引用支持结论，由当前智能体完成语义核对。
